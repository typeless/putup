# Config Deployment via Two-Pass Build

## Problem

Multi-project builds need per-subproject tup.config files. Manually creating them is error-prone and doesn't track changes.

**Goal:** A `configs/` subproject that outputs tup.config files, parsed and built *before* other subprojects.

## Core Insight

With a two-pass approach, this is just dependency ordering:

```
Pass 1: Parse configs/ → Build configs/ → Outputs tup.config files
Pass 2: Parse other subprojects (now have their configs) → Build everything
```

The `configs/` subproject is special only in that its outputs are consumed by the parser, not the compiler.

## Directory Structure

```
firmware/
├── Tupfile.ini
├── Tuprules.tup                     # Includes config layers, exports to subprojects
│
├── configs/                         # Config deployment subproject
│   ├── Tupfile                      # Rules that output tup.config files
│   ├── arch/
│   │   └── arm-v7.tup               # ARCH=arm, CROSS_COMPILE=...
│   ├── machine/
│   │   └── board-xyz.tup            # Includes arch, sets machine-specific vars
│   ├── distro/
│   │   └── router.tup               # Distro-specific settings
│   └── defconfigs/                  # Pre-built tup.config files (optional)
│       └── board-xyz/
│           ├── linux.config
│           └── uboot.config
│
├── linux/                           # Subproject using @() vars
│   └── Tupfile                      # Uses @(DEFCONFIG)
│
├── uboot/
│   └── Tupfile                      # Uses @(BOARD)
│
└── build-xyz/
    ├── tup.config                   # CONFIG_MACHINE=board-xyz
    ├── linux/tup.config             # Generated by configs/
    └── uboot/tup.config             # Generated by configs/
```

**Config layers (`.tup` files)** serve two purposes:
1. **In configs/Tupfile** - Control which/how tup.config files are generated
2. **In root Tuprules.tup** - Include them to export variables to all subprojects via `include_rules`

## configs/Tupfile (Examples)

The config deployment rules can use any method:

```tup
include_rules

# Include config layers - variables now available for use
include machine/@(MACHINE).tup
include distro/@(DISTRO).tup

# Option A: Copy pre-configured defconfig files (install -D creates parent dirs)
: defconfigs/$(MACHINE)/linux.config |> install -D %f %o |> $(TUP_VARIANT_OUTPUTDIR)/../linux/tup.config

# Option B: Generate from variables set by config layers
: |> echo "CONFIG_DEFCONFIG=$(LINUX_DEFCONFIG)" > %o |> $(TUP_VARIANT_OUTPUTDIR)/../linux/tup.config

# Option C: Custom script using config layer variables
: |> ./gen-config.sh $(MACHINE) $(DISTRO) %o |> $(TUP_VARIANT_OUTPUTDIR)/../linux/tup.config
```

**Example config layer:**
```tup
# configs/machine/board-xyz.tup
include $(TUP_CWD)/arch/arm-v7.tup

MACHINE = board-xyz
LINUX_DEFCONFIG = board_xyz_defconfig
UBOOT_BOARD = xyz
```

## Two-Stage Build

```bash
putup configure     # Stage 1: Execute rules that output tup.config files
putup               # Stage 2: Normal build (configs now exist)
```

### `putup configure` Command

Dedicated command for the config generation pass:

1. Scan project for Tupfiles
2. Parse all Tupfiles (using root tup.config only)
3. Identify rules where output ends with `tup.config`
4. Execute only those rules

**Why this works:**
- Config-generating rules only use @() from root tup.config (always exists)
- After `putup configure`, subproject tup.configs exist
- `putup` then parses everything with proper scoped configs

**Detection heuristic:** Output path ends with `tup.config`

**What else is needed:** Scoped tup.config loading, so stage 2 finds per-directory configs.

## Implementation

### Implemented: Scoped tup.config Loading

**Files:**
- `src/cli/context.cpp` - `find_config_for_dir()` function
- `include/pup/parser/eval.hpp` - Directory-specific config in EvalContext
- `src/graph/builder.cpp` - Variable nodes scoped to config directory

**Shipped behavior** (`find_config_for_dir`, `src/cli/context.cpp`):
- When parsing a Tupfile in `dir/`, collect every `tup.config` from `output_root/tup.config`
  down the chain to `output_root/dir/tup.config`
- Merge them root → leaf into a single config set
- On a key collision the PARENT config wins over the child (same authority model as
  Tuprules.tup `?=` defaults: the outer scope sets policy, inner scopes fill gaps)
- Cache loaded configs per directory

**Complexity:** Medium

### Implemented: `putup configure` Command

Shipped: `putup configure` is a real subcommand, exercised by the Makefile, CI, and the
`[configure]` E2E tests.

**Files:**
- `include/pup/cli/commands.hpp` - `cmd_configure` declaration
- `src/cli/cmd_configure.cpp` - Command implementation
- `src/cli/main.cpp` - Registers the subcommand

**Implementation:**
1. Scan project for Tupfiles (reuse existing scanner)
2. Parse all Tupfiles with root tup.config only
3. Build dependency graph
4. Filter to rules where any output ends with `tup.config`
5. Execute only those rules (reuse existing scheduler)

**Key difference from normal build:**
- Uses only root tup.config (ignores missing subproject configs)
- Executes subset of rules (config-generating only)
- Does NOT write index (avoids conflict with subsequent `putup` run)
- Config rules always execute (typically few and fast: install, cp, cat)

**What `putup` does with config rules:**
- Config-generating rules are in the graph like any other rule
- First `putup` after `configure`: may re-run them to record in index (harmless, they're fast)
- Subsequent `putup` runs: normal incremental logic applies

**Complexity:** Medium (filtering + partial execution)

## Design Decisions

1. **Scoping: Root → leaf merge** - `find_config_for_dir` merges every tup.config from the output root down to the Tupfile's directory; parent configs override children on key collision
2. **Two-stage: Explicit** - User runs `pup configure` then `pup`
3. **Detection: Output filename** - Rules outputting `*/tup.config` run in configure pass
4. **Config generation: User's choice** - install, cat, scripts, kconfig, custom tools

## Incremental Rebuild Tracking

- Config source changes → tup.config regenerated (tracked by pup like any output)
- tup.config changes → affected Tupfiles re-parsed
- @(VAR) creates Variable node → fine-grained command rebuild
