# Glob expansion — requirements

- area: glob-expansion
- required-legs: none

A glob is expanded during the parse and its result becomes a rule's inputs. The subject here
is that expansion: which paths a pattern names, in what order, what an exclusion removes, and
what the match itself names. See `README.md` for the format and the rules that apply to every
area.

This area requires no legs. Glob expansion carries no state across builds — it is a function
of the project and the filesystem — so its requirements are invariants of that function and
carry no `leg` field.

The area has no open gaps. The last one, #188, made the match set a function of parse traversal
order rather than of the project; the parse now iterates to a glob fixpoint, so a rule sees the
files its siblings generate whatever order they were parsed in.

---

## Group: pattern-recognition

When an input is a pattern at all, and how it decomposes.

### REQ-GLOB-CHARS

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "has_glob_chars"

putup shall treat a rule input containing an asterisk, a question mark, or an opening bracket
as a glob pattern.

### REQ-GLOB-SPLIT

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Glob split path"

putup shall split a glob pattern into the literal directory prefix that needs no matching and
the remainder that does.

### REQ-GLOB-STAR

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Glob pattern matching"

putup shall match an asterisk against any run of characters that contains no path separator.

### REQ-GLOB-QUESTION

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Glob pattern matching"

putup shall match a question mark against exactly one character, never against none.

### REQ-GLOB-RECURSIVE

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Glob pattern matching"

putup shall match a double asterisk against any number of path segments, including none.

### REQ-GLOB-CLASS

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Glob pattern matching"

putup shall match a bracketed character class against exactly one character drawn from that
class.

## Group: match-set

Which paths a pattern names.

### REQ-GLOB-SOURCES

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: A glob matches source and generated files together"
- discharge: test "GraphBuilder glob expansion - filesystem"
- discharge: test "GraphBuilder glob expansion - generated files"

putup shall expand a glob to both the source files on disk and the files produced by the
project's rules.

### REQ-GLOB-FILES-ONLY

- conformance: tup-conformant
- reference: upstream `nl_add_path` expands a rule's glob through `tup_db_select_node_dir_glob` with directories excluded, so only normal and generated files match
- discharge: test "Scenario: glob expansion matches files and never directories"

putup shall expand a glob to the files it matches and never to a directory whose name it matches.

### REQ-GLOB-DEDUP

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: Out-of-tree, a generated file shadowing a source is one glob match and the source survives"

Where a generated file shadows a source file of the same name, putup shall include that path
once and leave the source file in place.

### REQ-GLOB-SIBLING

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: A glob reaching into a sibling directory counts each match once"

When a glob reaches into a sibling directory, putup shall include each matching path exactly
once.

### REQ-GLOB-PROJECT

- conformance: unclassified
- reference: upstream resolves globs from its completed node table; mechanism not read line-by-line
- discharge: test "Scenario: A glob's match set does not depend on the producing directory's name"
- discharge: test "Scenario: A glob sees files generated by a directory parsed after it"
- discharge: test "Scenario: A foreach glob instantiates a command for a later-generated file"

putup shall expand a glob to the same match set whatever order the project's Tupfiles were
parsed in.

### REQ-GLOB-SAME-TUPFILE-ORDER

- conformance: tup-conformant
- reference: upstream expands a glob against its node table when `execute_rule` reaches the rule and never re-parses a Tupfile for a file the same Tupfile generates later, so `: *.h |> ... |> all.txt` above `: |> touch %o |> gen.h` never runs, while the same pair in the other order runs over `gen.h` (measured in #470). putup's parse fixpoint seeds each round with what the previous round generated, and drops from that seed every path whose producing rule lives in the globbing rule's own Tupfile: an earlier rule there has already put its output in the graph when the glob runs, and a later one must stay invisible. The stability check skips the same producers, or the dropped match would read as a parse-order dependence. Producers in other directories still count in either order (REQ-GLOB-PROJECT) (#470)
- discharge: test "Scenario: A glob does not see a file a later rule in the same Tupfile generates"

If a rule's glob would match a file that a rule written later in the same Tupfile generates, then
putup shall leave that file out of the glob's matches.

### REQ-GLOB-SAME-TUPFILE-INPUT-RESOLVES

- conformance: deliberate-deviation
- reference: upstream resolves an explicitly named input when `execute_rule` reaches the rule, and refuses one with no node yet with "tup error: Explicitly named file '%s' not found in subdir '…'" (`nl_add_path`, the `!tent` branch without full_deps), so on a fresh database a file only a later rule in the same Tupfile generates is refused (read from the code, not measured against a tup binary). putup links the input when the rule is read and upgrades the node in place when its producer appears (REQ-VARIANT-UNRESOLVED-UPGRADE), so the rule's position does not matter. A named file means the same thing wherever its producer is written, unlike a glob, whose match set depends on what exists when it runs (REQ-GLOB-SAME-TUPFILE-ORDER), so refusing would only reproduce upstream's single pass. examples/bsp's gcc/gcc Tupfile relies on it: it names tree-check.h as an order-only input above the rule generating it. It lives in this area beside REQ-GLOB-SAME-TUPFILE-ORDER because no area covers plain input operands
- discharge: test "Scenario: An input only a later rule in the same Tupfile generates resolves to that rule's output"

If a rule names a file as a regular or order-only input and a rule written later in the same
Tupfile generates it, then putup shall order the consuming command after the producing one.

### REQ-GLOB-NO-MATCH-NO-COMMAND

- conformance: tup-conformant
- reference: upstream runs a rule only when its expanded input list is non-empty or its input section was written empty (`execute_rule`, `r->inputs.num_entries > 0 || r->empty_input`), so `: *.o |> ld %f |>` with no objects generates no command while `: |> script |>` runs once; the test is on the user's text, so a section that is one variable evaluating to nothing also generates none. Measured against tup over `a.c` alone: `: *.none |> echo hi > %o |> out.txt` and the same rule spelling `%f` write nothing and exit zero, `SRCS =` / `: $(SRCS) |>` writes nothing, and `: *.none a.c |>` runs over `a.c`. putup meant to skip the same case but counted the glob's own placeholder operand as an input, so the rule ran with every input flag expanded to nothing; the guard now counts operands that name a file or a group, which is also what lets a rule over a glob that matches only files another directory generates pass its first parse and be re-parsed at the fixpoint rather than refused; a producer later in the same Tupfile is not seen, REQ-GLOB-SAME-TUPFILE-ORDER. A bang macro with a `!name.EMPTY` variant runs that variant over the empty match instead, REQ-GLOB-EMPTY-BANG-VARIANT. A glob whose directory nothing provides never reaches this guard's empty match: the parse refuses it, REQ-GLOB-ABSENT-DIR-REFUSED (#463)
- discharge: test "Scenario: A rule whose glob matches nothing produces no command"
- discharge: test "Scenario: A glob's match set does not depend on the producing directory's name"

If a rule is not foreach, its input section is written non-empty, no input operand names a file
or a group after expansion, and its command names no bang macro with an `.EMPTY` variant, then
putup shall generate no command for it.

### REQ-GLOB-EMPTY-BANG-VARIANT

- conformance: tup-conformant
- reference: upstream, when a rule's inputs evaluate to an empty list and its command is a bang macro, looks up the macro named by the command with `.EMPTY` appended and, when one is defined, runs the rule through that macro over the empty list (`execute_rule`, the t2066 branch, and `parse_empty_bang_rule`, parser.c:1870); the variant replaces the command, supplies outputs when the rule wrote none, and adds its extra outputs and order-only inputs, as any bang macro does (`parse_bang_rule_internal`). A foreach rule, whether the rule or its macro says foreach (REQ-OPERAND-FOREACH-FROM-MACRO), never reaches that branch, and `%f` inside the variant is refused as over any empty input list (REQ-OPERAND-INPUT-FLAGS-NO-INPUTS). Upstream's t2066 reaches the branch through a bin no rule filled; the test also covers a glob that matched nothing (#468)
- discharge: test "Scenario: A bang rule whose inputs come out empty runs the macro's .EMPTY variant"
- discharge: test "Scenario: A bang macro declared foreach makes the rule that invokes it foreach"

If a rule is not foreach, its input section is written non-empty, no input operand names a file
or a group after expansion, and its command names a bang macro `!name` for which `!name.EMPTY` is
defined, then putup shall generate the rule's command from `!name.EMPTY`.

### REQ-GLOB-ABSENT-DIR-REFUSED

- conformance: deliberate-deviation
- reference: upstream refuses an input path whose directory has no node, "tup error: Failed to find directory ID for dir '%s' relative to '…'" (`path_list_fill_dt_pel`, parser.c:2523), and skips a path outside the tup hierarchy; a directory gets a node from the source tree or when a rule parsed earlier names an output inside it, so upstream on a fresh database refuses `m/Tupfile`'s `: ../b/*.q |>` when the rule writing `../b/gen.q` lives in `n/`, parsed after `m/`, and accepts it when the producer is `a/` (read from the code, not measured against a tup binary). putup refuses after the parse fixpoint, when no rule anywhere in the project writes inside the directory, so the verdict does not depend on parse order (REQ-GLOB-PROJECT). A build scoped to some directories parses only those and cannot rule out a producer outside the scope, so it does not refuse. A plain input path, regular or order-only, shares the refusal, since upstream applies it to every input path list (`path_list_to_nl` → `parse_dependent_tupfiles`, regular and order-only alike). Upstream has one tree; putup resolves an input from the source tree, then the config tree, then the build tree, and the refusal counts the first two, not a build-tree directory an earlier build left on disk, so the verdict does not depend on build history; an input spelled through the build directory is compared with that prefix removed. A rule later in the same Tupfile does not provide the directory, as REQ-GLOB-SAME-TUPFILE-ORDER keeps such a rule's outputs out of a glob. It lives in this area because no area covers plain input operands (#469)
- discharge: test "Scenario: An input inside a directory nothing provides is refused"

If an input path or glob names a directory inside the project that neither the source tree, the
config tree, an earlier rule in the same Tupfile, nor a rule in another Tupfile writes inside, then
putup shall refuse the parse and name the input.

## Group: ordering

A rule's inputs reach its command line through `%f`, so match order is observable output.

### REQ-GLOB-ORDER

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: glob expansion orders matches by path, not by interning order"

putup shall order a glob's matches by path rather than by the order the paths were interned.

### REQ-GLOB-BUILDDIR

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: A glob's %f order does not depend on the build directory's name"

putup shall order a glob's matches independently of the name of the build directory.

### REQ-GLOB-STABLE

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: A glob over generated files is path-ordered and stable across builds"

putup shall order a glob's matches identically on every build of an unchanged project.

## Group: exclusions

What `!pattern` removes from a match set.

### REQ-GLOB-EXCL-LITERAL

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: An exclusion applies to generated glob matches out-of-tree"

When a rule names an exclusion that is a literal path, putup shall remove that path from the
match set whether the build is in-tree or out-of-tree.

### REQ-GLOB-EXCL-PATTERN

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: An exclusion that is itself a glob applies to generated matches out-of-tree"

When a rule names an exclusion that is itself a glob, putup shall remove every path it
matches from the match set, generated files included.

### REQ-GLOB-EXCL-STABLE

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: A glob exclusion's match set does not depend on what exists on disk"

putup shall remove the same paths for a glob exclusion whatever files exist on disk when the
rule is parsed.

### REQ-GLOB-EXCL-BIN

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: An exclusion applies to bin members out-of-tree"

When a rule names an exclusion and consumes a bin, putup shall remove the matching members
from its inputs whether the build is in-tree or out-of-tree.

### REQ-GLOB-EXCL-SENTINEL

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: An exclusion does not erase a group reference or the pattern it filters"

When a rule's input list holds a group reference or a pattern that has not been expanded,
putup shall leave that entry in place while applying an exclusion.

### REQ-GLOB-EXCL-SPELLING

- conformance: unclassified
- reference: upstream mechanism not read
- discharge: test "Scenario: An exclusion matches an input spelled with the build-directory prefix"

When a rule names an input with the build directory's prefix, putup shall apply an exclusion to
it as if it had been named without that prefix.

### REQ-GLOB-EXCL-HIDDEN

- conformance: unclassified
- reference: upstream mechanism not read; a decided widening of filesystem-expansion semantics, not inherited from them
- discharge: test "Scenario: A glob exclusion matches a hidden file the same as any other"

putup shall apply a glob exclusion to a hidden file on the same terms as to any other file.

## Group: match-extraction

What `%g` names, and where it is resolved.

### REQ-GLOB-MATCH-COMMAND

- conformance: unclassified
- reference: `docs/reference.md` documents `%g` as the glob match portion in its %-flag table; upstream not read
- discharge: test "Scenario: A foreach rule substitutes %g in its command, not only in its output name"

putup shall substitute a foreach rule's glob match into the rule's command text as well as
into its output names.
